# Ontology

Generated by `python -m docfactory.ontology.ontology_render`; do not edit. Entities and facts come from the entity models,
tagging signals from `docfactory/ontology/signals.json`.

Ingestion splits each original into chunks and tags every chunk with the entities it informs: a **heading term** in the chunk's
heading trail (inherited by sub-sections) or an **identifier pattern** in its text is strong evidence; **keywords** are weak
evidence. Chunks the signals cannot tag go to the LLM fallback.

## ApplicationOverview

High-level overview of one software application: why it exists, who it serves and what it does.

Keys: `{app}.ApplicationOverview`, `{app}.Components.{component}.ApplicationOverview`

**Facts**

- `application_name`: Official name of the application as used in documents, e.g. KitchenHQ.
- `purpose`: One to three sentences on why the application exists and what problem it solves, e.g. 'Lets kitchen staff plan orders and track stock in one place.' A good value states the problem and the outcome, not the technology.
- `business_overview`: Business context: the business area or process the application supports and the value it brings, e.g. 'Supports daily food ordering for all restaurants of the group and reduces waste.' A good value is a short paragraph a non-technical reader understands.
- `business_owner`: Person, role or department accountable for the application from the business side, e.g. 'Head of Operations'.
- `target_users`: The kinds of users or user groups that use the application, one entry per group, e.g. ['Kitchen staff', 'Restaurant managers'].
- `key_capabilities`: The main things the application can do, one short statement per capability, e.g. ['Create and approve purchase orders', 'Track stock levels'].
- `out_of_scope`: Things the application deliberately does not do, one statement each, e.g. ['Payroll processing'].
  - `reason`: Why the question does not apply, in one sentence, e.g. 'The application is a batch job and has no web UI.' Never empty and never a placeholder such as 'n/a'.
- `business_criticality`: How important the application is to the business and what an outage means, e.g. 'Tier 1 - business critical, orders stop without it'.
- `lifecycle_status`: Where the application is in its life, e.g. 'In production', 'Under development' or 'Being retired'.
- `go_live_date`: Date the application went (or goes) live, ISO format YYYY-MM-DD, e.g. 2024-03-01.
  - `reason`: Why the question does not apply, in one sentence, e.g. 'The application is a batch job and has no web UI.' Never empty and never a placeholder such as 'n/a'.
- `technology_summary`: Short plain-language summary of the technology the application is built on, e.g. 'Python web service with a PostgreSQL database, hosted on Azure'.
- `related_systems`: Names of other applications or systems this application depends on or exchanges data with, one per entry, e.g. ['ERP', 'Payment gateway'].

**Tagging signals**

- Heading terms: `introduction`, `purpose`, `project scope`, `product scope`, `overview`, `overall description`, `product perspective`, `product functions`, `executive summary`, `business objectives`, `background`, `intended audience`, `user classes`, `stakeholders`
- Identifier patterns: _none_
- Keywords: `purpose`, `objective`, `stakeholder`, `target users`, `business owner`, `in scope`, `out of scope`, `beneficiaries`

## Architecture

The architecture of an application or of one of its components: style, technology stack, components, data stores and integrations with other systems.

Keys: `{app}.Architecture`, `{app}.Components.{component}.Architecture`

**Facts**

- `architecture_style`: Overall architectural style, e.g. 'Modular monolith' or 'Microservices behind an API gateway'.
- `technology_stack`: Main technologies used, one entry each, e.g. ['Python 3.12', 'PostgreSQL 16'].
- `components`: The components of the architecture, one entry each, e.g. a component named 'Order API'.
  - `name`: Short name of the component, e.g. 'Web front end' or 'Order API'.
  - `purpose`: What the component does and why it exists, e.g. 'Serves the browser UI and forwards requests to the Order API.' Leave empty when not yet described.
  - `technology`: Main technology or framework the component is built with, e.g. 'Python 3.12 / FastAPI'.
  - `owner`: Role or team responsible for the component, e.g. 'Platform team'.
  - `dependencies`: Names of the other components, services or libraries this component depends on, e.g. ['Order database', 'Payment gateway'].
- `data_stores`: The data stores used, one entry each, e.g. a store named 'Orders database'.
  - `name`: Short name of the data store, e.g. 'Orders database'.
  - `store_type`: Kind of store, e.g. 'relational database', 'object storage', 'message queue', 'file share'.
  - `technology`: Product and version of the store, e.g. 'PostgreSQL 16'.
  - `contents`: What data the store holds, e.g. 'Customer orders and order line items.' A good value describes the data, not just the technology.
- `integrations`: The integrations with other systems, one entry each, e.g. an integration named 'Payment gateway'.
  - `name`: Name of the other system the application integrates with, e.g. 'Payment gateway'.

  - `purpose`: Why the integration exists, e.g. 'Submits payment requests and receives payment confirmations.' Leave empty when not yet described.

  - `authentication`: How the connection is authenticated, e.g. 'OAuth 2.0 client credentials'.
- `diagram_reference`: Relative path with forward slashes to an architecture diagram, e.g. 'docs/diagrams/architecture.png'.
  - `reason`: Why the question does not apply, in one sentence, e.g. 'The application is a batch job and has no web UI.' Never empty and never a placeholder such as 'n/a'.
- `notes`: Free-text context about the architecture, e.g. 'The reporting component is being replaced in 2027.' Leave empty when there is nothing to add.

**Tagging signals**

- Heading terms: `architecture`, `system design`, `technical design`, `technology stack`, `components`, `data model`, `software interfaces`, `communication interfaces`, `system interfaces`, `integration`
